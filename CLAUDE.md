# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
# Build
cargo build                                  # debug
cargo build --release                        # produces ./target/release/holmes
cargo check --workspace                      # fast type-check across all crates

# Test
cargo test --workspace                       # full suite
cargo test -p holmes-runtime                 # one crate
cargo test -p holmes-harness scenario        # tests in crates/holmes-harness/tests/scenario.rs
cargo test -p holmes-cli slash_commands::    # filter by test path
cargo test <name> -- --nocapture             # see println / tracing output

# Dependency policy (CI `deny` job; exemptions + review dates live in deny.toml)
cargo deny check                             # licenses / bans / advisories / sources

# Run
./target/release/holmes                      # inline (Claude-Code-style) TUI (default)
HOLMES_CLASSIC_TUI=1 ./target/release/holmes # legacy full-screen TUI (fallback)
./target/release/holmes repl                 # legacy Reedline REPL
./target/release/holmes -q "question"        # one-shot, non-interactive
./target/release/holmes -c                   # continue most recent session
./target/release/holmes -r <session-id>      # resume specific session
./target/release/holmes setup                # interactive provider/model wizard
```

LLM: only the Anthropic Messages wire protocol is implemented (`/v1/messages`). Any Anthropic-compatible gateway works by adding it as another entry under `llm.providers`. `ANTHROPIC_API_KEY` and `HOLMES_API_KEY` are auto-detected during `setup`. Default config lives at `~/.local/share/holmes/config.yaml`; `config.default.yaml` at the repo root is the reference template.

Harness scenarios (deterministic LLM replay tests) live in `scenarios/*.yaml` and are driven by `crates/holmes-harness/tests/scenario.rs` — add a YAML, the runner picks it up. Reliability/fault-injection scenarios use tool `delay_ms` (hung tool) plus scenario-level `config.execution` (tool/turn deadlines) and `config.permissions` (e.g. `mode: ask`) overrides. Structured-event and metrics conventions live in `docs/observability.md`; operator recovery procedures in `docs/runbooks/agent-recovery.md`.

## Architecture

### Crate dependency direction

`holmes-core` is the base layer (types, `Event`, `Config`, `RuntimeSession`, `AgentHook` trait, `SubagentRunner` trait, the four-zone `AttackState` in `state/`). Everything else depends on it. The runtime layer (`holmes-runtime`) sits above the storage/LLM/tool/guard/mind-palace crates and is consumed by `holmes-cli` and `holmes-harness`. `holmes-browser` (native CDP automation) depends only on `holmes-core` and is surfaced as the `browser` tool in `holmes-tools`. **The runtime is the single agent loop** — there is no separate `agent_loop.rs` anywhere (a prior one was removed); both interactive turns and one-shot queries go through `holmes_runtime::runtime::AgentRuntime`.

Note: `holmes-runtime/src/lib.rs` re-exports most submodules but **not `runtime` itself**. Callers must write `holmes_runtime::runtime::AgentRuntime` (this trips up `use` statements).

### What one turn actually does

The docs' "LLM → Permission → Guard → Tool → Guard → Yield" picture is incomplete. The real `AgentRuntime::run_turn` orchestrates 10 engines per iteration:

```
on_session_start (middleware, fires every turn despite the name)
record UserMessage event
memory.recall_for_turn         ← top-3 semantic recall into context
loop:
  cancel-flag check                    ← context.cancel set? → emit notice; return Interrupted
  drain_steering                       ← mid-turn operator interjections injected (safety point)
  drain_background_tasks               ← finished background subagents injected (same safety point)
  reflection.assess_iteration_budget   ← max-iterations gate
  maybe_compact                        ← at most once per turn; emits CompactionBoundary
  perception.perceive                  ← builds a frame from RuntimeContext
  deliberation.decide                  ← LLM call → ParsedDecision (decision + meta_actions)
  middleware.on_token_usage / record assistant response
  apply_meta_actions                   ← SetGoal attached to THIS step, applied first
  match HolmesDecision:
    Answer              → completion gate when the task is gated (goal / TaskContract /
                          tool activity); exempt pure chat answers return directly
    Finish              → always through the same completion gate
    ProtocolViolation   → feedback note; stay in loop (finish/ask_watson mixed with tools)
    AskWatson           → emit NeedsUserInput; return NeedsUser
    UseTools            → action.execute_batch (Permission → AgentHook.pre → middleware.before_tool_call → tool → middleware.after_tool_call → AgentHook.post)
                          → typed evidence records → evidence.project → memory.remember_observations
    SetGoal             → record event + emit PlanUpdate (stay in loop)
  middleware.after_step
```

`HolmesDecision` has **six** variants: `Answer`, `AskWatson`, `UseTools`, `SetGoal`, `Finish`, `ProtocolViolation`. `SetGoal` is the one loop-internal (non-terminal) outcome, not a terminal state. `TurnOutcome` exits with `FinalAnswer`, `NeedsUser`, `MaxIterationsReached`, or `Interrupted`. (An earlier `deduce`/`reflect` "ledger" was removed — the model reasons in plain text instead, per the AI-native direction; see below.)

**Unified completion gate (P0-02).** Every terminal outcome — `Finish` AND a plain-text `Answer` on a gated task — passes through `runtime.rs::run_completion_gate` → `completion.rs::CompletionVerifier`. The gate trigger is deterministic (`TaskControlState::completion_gate_required`: standing goal, derived `TaskContract`, or any tool activity this session); pure chat meets none of them and is exempt. A `TaskContract` (`task_contract.rs`) is derived from the user's request by fixed heuristics (target tokens × action verbs), not by the model's say-so; its requirements are target-relevant action evidence (deterministic — bookkeeping calls like `write_todos` and target-irrelevant calls never count) plus the semantic objective, judged by an independent verifier call routed through the `goal_evaluator` role with fixed system instructions and tool output encoded as delimited untrusted data. Successful tool calls are recorded as typed `EvidenceRecord`s (call id, contract id, normalized input, output SHA-256, per-class predicate, timestamp). Rejected claims feed the gaps back into the loop; when `supervisor.max_verification_retries` is exhausted the turn ends as an explicit partial result listing the remaining work.

**Steering & background-task safety point.** `RuntimeContext.steering` (a shared `SteeringQueue`) collects operator lines typed while a turn is in flight; `run_turn` drains it at every iteration boundary (`drain_steering`), wrapping each line as `<operator_message>…</operator_message>`, recording it as a durable `Event::UserMessage` (the event log stays the source of truth), and echoing `RuntimeYield::SteeringInjected` so the UI can confirm it landed — the very next perception/deliberation already sees the correction. The same boundary also drains **finished background subagents** (`drain_background_tasks`): each completion is injected exactly once as a `<system-reminder>`-wrapped user message plus a `RuntimeYield::BackgroundTaskFinished` yield, so results surface poll-free; a final drain at every turn exit folds in tasks that finished during the last LLM call, and tasks still running at turn end stay in the registry for the next turn's first drain. Delivery is **durable** (P1-02): the drain first delivers every terminal, not-yet-delivered task for this session straight from the `tasks` table, and each delivery appends the reminder event and marks the task `delivered` in ONE transaction (`SessionStore::deliver_task_result`) — a crash can leave a result undelivered (re-delivered next turn/restart) but never half-presented or duplicated. Durable tasks are leased under a fencing token (`attempt`): heartbeat/checkpoint/terminal writes must match owner+token, a heartbeat reporting a lost lease cancels the worker and forbids its write-back, and a resident `DurableTaskScheduler` (`holmes-runtime/src/scheduler.rs`, spawned by the CLI) periodically reaps dead-owner/expired leases and re-executes requeued tasks from their persisted payload. Lines pushed after a turn's last drain remain in the queue; the CLI re-routes those into `ChatContext.queued_turns` (`chat.rs::transfer_steering_leftovers`) as follow-up turns. Approval-rejection feedback goes through the same queue, so the agent sees *why* a call was denied.

**Decisions travel over native tool_use, not scraped JSON.** The three non-`UseTools`/`Answer` decisions are advertised to the model as synthetic control tools (`decision.rs::control_tool_definitions` = `set_goal` / `ask_watson` / `finish`, appended to the tool list in `deliberation.rs`) and intercepted by name in `ParsedDecision::from_response` — the model calls them like any tool, so their arguments are API-validated structure, not `<holmes_decision>{…}</holmes_decision>` blobs pulled out of prose (that text path survives only as a deprecated fallback). `set_goal` is a **meta-action**: the model may emit it in the SAME response as executable tool calls, and `apply_meta_actions` runs it before the primary decision — so recording a goal and acting on it happen in one iteration instead of two round-trips. `ask_watson`/`finish` are terminal and must be emitted ALONE: a response mixing a terminal control call with executable tool calls parses as `ProtocolViolation` — nothing in it is executed and the model is asked to re-emit the parts in separate steps.

**Parallel tool execution.** `action.rs::execute_batch` dispatches: a batch of >1 call where **every** tool is concurrency-safe — a read-only registry tool **or `spawn_subagent`** (`ToolRegistry::can_parallelize`) — runs the slow tool `execute()` I/O concurrently (`futures::join_all`), while all state mutation (permission/guard gating, events, guard-post, messages) stays sequential and in original order. Any other batch takes the fully sequential path. Subagents qualify because each runs in an isolated `RuntimeContext` and the shared stores (`SessionDB` is `Arc<Mutex<Connection>>`, `MemoryStore`, rate-limited `LlmClient`) serialize internally — so a fan-out of `spawn_subagent` calls reasons in parallel while DB writes serialize safely. The parallel gating pass (Pass A) still consults the `ApprovalHandler` for mutating calls (e.g. subagents) in `ask` mode before they join the concurrent set. Read-only tools include `read_file` / `grep` / `glob` / `http_request` / `web_fetch` / `read_pdf` / `get_task_output` / browser reads. (`web_fetch` fetches a URL and returns HTML-stripped readable text; `read_file` reports binary files cleanly instead of erroring on non-UTF-8.)

**Cognitive kernel and epistemic state.** The obsolete `deduce` transcript-ledger engine, `reflect` meta-action, and unused MindPalace context/dashboard layers were removed. They are not the current Hypothesis Ledger. The replacement has two bounded parts: `CognitiveEngine` performs Fast/Adaptive/Deep private propose/critique/commit passes without persisting raw reasoning; case-scoped Hypothesis Ledger v2 persists only typed Hypotheses, Predictions, Experiments, Evidence, Resolutions, and bounded public commit rationale. `SkepticGate` is no longer the authority for strong claims: Confirmed/negative findings require Runtime-owned `_ledger_validation` derived from an existing Resolution; unattested claims are downgraded to Candidate. `[Current situation]` remains projected live from `AttackState`; the Ledger projection is injected separately. Long-term recall is lexical (FTS5/LIKE), not embedding-based.

**Turns are interruptible.** `RuntimeContext.cancel` (`Arc<AtomicBool>`, shared via `set_cancel_flag`) is checked at each loop boundary; when set, `run_turn` cleanly finishes (records `turn_complete`) and returns `Interrupted`. Both UIs wire this: the classic TUI spawns an interrupt watcher (`tui.rs::spawn_interrupt_watcher`); the inline UI flips the flag in `inline_ui.rs::dispatch_busy_key` on Esc/Ctrl+C — its single input thread (`ui::input::InputThread`) owns stdin for both the idle and busy loops, so no second reader races it. Cancellation is cooperative at iteration boundaries — an in-flight LLM call or tool completes first.

### Three independent safety layers (don't confuse them)

| Layer | Where | What it does |
|---|---|---|
| `PermissionPolicy` (`holmes-runtime/src/permissions.rs`) | Per tool call, inside `action.execute_batch` | User-facing authorization. Modes: `default / plan / read_only / accept_edits / dont_ask / ask / bypass`. Allow/deny glob lists. |
| `GuardChain` (`holmes-guards`) | Pre-tool (block) and post-tool (extract into `AttackState`) | System-level. `SkepticGate` records findings, but strong confidence is accepted only with Runtime-owned Ledger attestation tied to a verified Resolution; otherwise it records Candidate. PreGuards: `scope`, `immutable_field`, `dangerous_command`, `repetition`, `file_tracker`. `ScopeGuard` is always installed and becomes fail-closed for recognized egress targets when `guards.scope.allow` is non-empty. PostGuards: `attack_surface`, `evidence_extractor`, `skeptic_gate`, `failure_tracker`, `soft404`, `file_tracker`, `plan_tracker`. |
| `RuntimeMiddleware` (`holmes-runtime/src/middleware.rs`, newer) | Cross-cutting: `on_session_start / before_step / after_step / before_tool_call / after_tool_call / before_event_persist / on_token_usage / on_final_answer` | Built-ins: `GuardMiddleware` (static dangerous-command backstop — now targets the real `execute_command`/`command`, and is actually installed in the CLI path), `SensitiveDataRedactMiddleware` (regex redaction — key=value plus standalone JWT/PEM/AWS/bearer shapes), `UntrustedContentMiddleware` (fences target-controlled output from `web_fetch`/`http_request`/`browser` in an `<untrusted-target-content>` boundary so a booby-trapped page can't inject instructions), `RateLimitMiddleware` (sliding-window outbound egress throttle set by `safety.egress_rpm`, anti-DoS distinct from LLM RPM), `TokenAuditMiddleware` (budget), `UserHookMiddleware` (runs operator-configured shell hooks from `config.hooks` around tool calls — `before_tool` hooks with `blocking: true` that exit non-zero **veto** the call with stderr as the reason; `after_tool` hooks are advisory; hook sees `$HOLMES_TOOL_NAME` + args JSON in `$HOLMES_TOOL_ARGS`/stdin; matcher = exact / `*` / `prefix*`). The CLI bootstrap (`chat.rs`) installs redaction + untrusted-content + GuardMiddleware always, RateLimit when `safety.egress_rpm` is set, and UserHookMiddleware when `config.hooks` is non-empty. |

Live caveats:
- `GuardMiddleware` checks `args.get("CommandLine")` (PascalCase) — the actual `execute_command` tool uses lowercase keys; this guard is currently a no-op for real calls.
- `AgentRuntime::new` auto-installs a `CheckpointHook` into `action.hooks`; it's not configurable from outside. Since P1-05 the hook checkpoints into the persistent per-session directory (`<sessions_dir>/<session-id>/checkpoints/`, falling back to system temp only when the session store has no on-disk dir), keyed by `sha256(canonical_path)+nanos+uuid` with a JSON manifest (pre/post hashes, sizes, reason, session id) and tombstones for newly created files; `restore_latest_checkpoint` matches manifests exactly and verifies payload hashes.
- `AgentRuntime` itself does **not** install a `GuardChain::from_config` — only the CLI bootstrap (`chat.rs`, `subagent.rs`, `tui.rs`) does. Constructing `AgentRuntime` directly (e.g. in custom harness code) without first wiring guards silently disables all PostGuard data flow: `attack_surface`, `evidence_bundle`, and the `findings` validated zone remain empty, and `evidence.project` produces no observations. The harness `runner.rs` and `RuntimeContext::permissive_attack_state` both bypass this on purpose for tests, but it's a sharp edge.

### State partitioning — `holmes-core/src/state/`

`AttackState` is split into four explicit zones with disciplined writers:

- **Immutable** (`immutable.rs`) — target URL/IP, challenge metadata. Constructed once via `pub(crate) new`, no setters anywhere.
- **Tool truth** (`tool_truth.rs`) — `AttackSurface`, `EvidenceBundle`, credentials, object refs. Written **only by PostGuards** from raw tool output.
- **Validated** (`validated.rs`) — `Finding`s (now carry `severity`/`location`/`evidence_source`) with `FindingConfidence`. The blessed writer is `AttackState::record_finding(finding)` — **monotonic** (a weak restatement never demotes a `Confirmed`) — plus `record_and_persist_finding`, which also queues the finding so the runtime emits a durable `Event::FindingRecorded`. Findings therefore **survive turn boundaries and resume**: `run_turn` replays them back via `RuntimeContext::seed_findings_from_history` (the in-memory `AttackState` is rebuilt each turn). `confidence: not_vulnerable` records a `Rejected` finding — the ruled-out coverage ledger, rendered separately (`Ruled out …`) so "tested-and-safe" is distinct from "never tried". `SkepticGate` uses these; production code outside SkepticGate should not call the writers. `findings_mut()` still exists (raw) but is doc-marked as test-fixture / SkepticGate-only — calling it from new production code breaks the validated-zone contract.
- **Free** (`builders.rs`) — phase, scratch fields, aggregator. Mutable everywhere.

If you find a writer to the wrong zone, that is a real bug — the comments call this out as a design invariant.

### Event sourcing model

Every state change is an immutable `Event` (40+ variants in `holmes-core/src/event.rs`) appended to `SessionDB` (SQLite + FTS5 + WAL). Sessions reconstruct by replaying events; **`MindPalace::from_events` is the canonical rehydrate path**. Forking is a transactional event copy at a chosen index. Token deltas are accumulated separately via `update_token_counts`.

`holmes-session/src/store.rs` defines the `SessionStore` async trait (14 methods); `SessionDB` implements it. Downstream code (`MindPalace`, harness `runner.rs`, subagent runner) takes `Arc<dyn SessionStore>` — prefer the trait when introducing new consumers so tests can substitute an in-memory store.

When a `ToolResult.content` exceeds 10 000 chars, `SessionDB::append_event` offloads it **into the SQLite blob tables** (`blobs`/`blob_chunks`, zlib-compressed when smaller, content-addressed by SHA-256, inserted in the same transaction as the event row) and rewrites the in-event content to a `__BLOB_REF__:sha256:<hex>` marker; `get_events` restores the payload transparently (verifying hash/size) so the database alone is the authority. Pre-v6 `__BYPASS_FILE__:file://` sidecar pointers still read (degrading to the pointer when the file is lost). `transcript.jsonl` is a derived projection: one bounded-queue worker per database path (shared across `SessionDB` handles), per-session offsets persisted in `projection_state`, and `SessionDB::open` auto-reconciles missing/truncated transcripts against the events table.

### Mind Palace (now just the memory layer)

`holmes-mind-palace::MindPalace` wraps a single **memory layer** — raw `session_events: Vec<Event>` mirrored on every `MindPalace::ingest(event)`, plus a handle to the long-term cross-session `MemoryStore` (SQLite FTS5). Rehydrates via `MemoryLayer::replay` (`SessionStore::get_events`). Recall itself runs in `holmes_runtime::MemoryEngine` (lexical FTS5/LIKE), not here.

The old typed **context layer** and **dashboard layer** were removed: they were fed by situational events (`AttackSurfaceUpdate`, `VulnerabilityFound`, …) the runtime never emits, so they stayed empty and never reached the model, and the `/dashboard` command that rendered them is gone. The prompt's `[Current situation]` is projected live from `AttackState` in `perception.rs::situation_from_state`.

### Compaction

`CaseCompactor::plan` decides when to compact based on `compressor.threshold` over `context_limit`, preserving `protected_head` messages at the front and `protected_tail_tokens` tokens at the tail. The middle is summarized. The trigger estimate is `max(char/4 of messages, last actual prompt_tokens)` (`plan_with_floor`) — the char/4 estimate omits the system prompt + tool definitions and undercounts non-ASCII, so the runtime feeds the real `prompt_tokens` from the previous LLM call (`AgentRuntime.last_prompt_tokens`, set in `apply_usage`) as a calibrated floor. The static summary also **folds in the live structured state** (`situation_from_state` — findings with severity/location, discovered endpoints, ruled-out coverage) via `compress_session`'s `state_context`, so the compacted history keeps a real security checkpoint, not just "compacted N messages". On an actual API context-overflow the runtime **loops** force-compact + retry up to `MAX_OVERFLOW_COMPACTIONS` (`decide_with_overflow_retry`); if compaction can't shrink further (a single huge message in the protected head/tail), it falls back to `emergency_truncate_messages` (caps oversized message *content*, preserving message count + tool_use/tool_result pairing) before failing gracefully. Compaction only rewrites the in-memory message view; the event log is append-only (findings/attack-surface survive via `seed_findings_from_history`), and the summarized-away messages+events are copied to a `CompactionArchive` (never deleted). By default the middle is summarized with the static keyword template (`CompressionMethod::StaticFallback`); set `compressor.llm_summary: true` to instead summarize it with an LLM call (compressor role) — the runtime pre-computes the summary in `llm_summarize_middle` and passes it to `compress_session` (`CompressionMethod::LlmSummary`), falling back to static on any error. In `llm_summary` mode the runtime additionally **pre-fires the summary in the background** once usage enters a window 10% below the threshold (`maybe_spawn_prefire`, `PREFIRE_WINDOW = 0.10`, the grok-build two-pass prefire): a detached task summarizes the exact middle span, and when the threshold is later crossed with that span still intact (`SpanFingerprint` match, `take_matching_prefire`) the warmed summary is reused so compaction costs zero extra LLM latency; on any fingerprint mismatch or prefire failure the synchronous path simply re-runs. Separately, `compressor.pre_compact_flush` (default true, **`llm_summary` mode only**) runs a **pre-compaction flush**: just before the middle is folded away, the compressor role extracts the must-survive case state (confirmed findings / access & credentials / leads & hypotheses / ruled out & next steps), persists it to long-term memory (`remember_flush_note`, recallable in later turns), and prepends it to the summary as a `## Preserved critical state` section — best-effort, a flush failure never blocks compaction. Both mechanisms skip the static path entirely, so scripted harness replays see zero extra LLM calls. (The keyword-based `PitfallSummary` extraction was removed — pitfalls never reached the model.) `AgentRuntime::compact_now` exposes a manual entry point.

### Subagents

`SpawnSubagentTool` is registered only when a `SubagentRunner` is supplied. `holmes-cli/src/subagent.rs::CliSubagentRunner` mints a `sub-<uuid>` `RuntimeSession`, builds a **fresh** `MindPalace` and `GuardChain` from the parent's config but **shares the parent's `session_db`, `memory_store`, and `LlmClient`**. The captured final answer (from a `RuntimeYield::FinalAnswer`) becomes `SubAgentResult.summary`. Subagents are not isolated processes — they share the same SQLite store, so their events land in the same DB tagged under their sub-session id. **Parallel fan-out:** emitting several `spawn_subagent` calls in one response runs them concurrently (see "Parallel tool execution") — independent subtasks reason in parallel, and the tool description tells the model to do this.

**Background mode.** `spawn_subagent` takes `run_in_background` (default false — the synchronous path is unchanged). With `true` the tool validates the task schema synchronously, registers the task in a shared `BackgroundTasks` registry (`holmes-core/src/background.rs`), detaches the runner onto a tokio task, and returns a task id immediately; the detached task writes its outcome back into the registry, and the runtime injects it into the conversation at the next iteration boundary (see "Steering & background-task safety point"). The companion read-only tool `get_task_output` (registered alongside `spawn_subagent` in `builtin/mod.rs`, sharing the SAME registry handle the surface wires into the runtime context) queries a task by id and optionally blocks up to `wait_seconds` (≤60s) for completion — a short-poll loop that also breaks early on operator cancel. The inline UI's post-turn status line surfaces still-running tasks (`⏳ N background task(s) running`).

### Browser automation — `holmes-browser`

Native, **always-headed** browser automation over CDP via `chromiumoxide` (default-features off). The crate exposes one concrete struct, `BrowserManager` (`manager.rs`), not a trait: an `Arc<Mutex<ManagerState>>` holding the live `Browser` + a cached `Arc<Page>` + an `owned` flag, with async `navigate / click / fill / get_content / execute_js / screenshot / close`. Launch is **lazy** via the private `ensure_launched` — the browser opens on first action and stays open across turns.

- **One tool, one param.** Surfaces as the single agent tool `browser` (`holmes-tools/src/builtin/browser.rs`), dispatching on an `action` field (`navigate / click / fill / screenshot / get_content / execute_js`). `is_read_only()` is false; write actions are gated in `read_only` permission mode by `BrowserReadOnlyMiddleware` (see `action_is_read_only`). Registered in `builtin/mod.rs` **only when a `BrowserManager` is passed to `register_all`**.
- **Enabled by default; the model reaches for it on its own.** `config.browser.enabled` defaults **true** (lazy launch — Chrome only starts on the first browser action). When enabled, `project_knowledge.rs::BROWSER_GUIDANCE` is injected into the system prompt telling the agent to escalate from `http_request` to `browser` on its own (JS-rendered SPAs, login/2FA/CAPTCHA walls, DOM/JS inspection, screenshots). The tool is not advertised in the prompt when disabled.
- **Lifecycle: `chat.rs` (shared by TUI + REPL).** `create_chat_context` builds the manager via `build_browser(config, data_dir, session_id)` for **fresh, resumed, and continued** sessions alike, stores it on `ChatContext.browser`, and wires `/browser close` (next action relaunches). `subagent.rs` still does not wire a browser.
- **Attach vs. launch.** If `browser.cdp_endpoint` is set, it `Browser::connect`s to your already-running Chrome (`owned = false`, so `close` only drops the handle — never kills your browser). Otherwise it launches a per-session profile at `<sessions>/<session-id>/browser-profile` with stealth flags (`disable-blink-features=AutomationControlled` + a `STEALTH_JS` init script).
- **Anti-bot via real Chrome.** With no `executable_path`, `detect_system_chrome()` probes hardcoded Chrome/Edge/Chromium/Brave install paths and prefers a real system binary over chromiumoxide's downloaded Chromium — a real binary defeats strong fingerprinting (Akamai etc.).
- **Self-healing launch.** `ensure_launched` runs a 1s `LIVENESS_PROBE` (`page.evaluate("1")`); a dead background CDP handler discards the stale page/browser and triggers a fresh launch on the same profile (logins survive) instead of looping on "receiver gone".
- **Sandbox is non-negotiable.** `sanitize_launch_args` rejects `--no-sandbox` / `--disable-web-security` and similar in `extra_launch_args` (`FORBIDDEN_LAUNCH_FLAGS`).
- **Login handoff.** For a human step (login / 2FA / CAPTCHA) the agent emits `AskWatson`, pauses, and continues on the same authenticated page after you reply `continue`.

Config key `browser` (`holmes-core/src/config.rs::BrowserConfig`): `enabled`, `content_limit`, `timeout`, `proxy`, `ignore_https_errors`, `executable_path`, `extra_launch_args`, `screenshot_dir`, `cdp_endpoint` — all consumed. v1 is always headed (the former `headless`/`vision` fields were removed in the P2-01 cleanup; startup diagnostics flag them in old configs).

### CLI surfaces

`holmes` with no args starts the **inline TUI** (`inline_ui.rs`, ratatui 0.30 `Viewport::Inline`) — Claude-Code-style: renders in the main terminal buffer with a two-layer model — completed output is frozen into native scrollback via `Terminal::insert_before` (immutable once committed; scroll/select/copy work natively), and only a small live region at the bottom is redrawn per frame. The live region is laid out `[approval card][markdown tail][@completion list][input box][status line]`; its height is dynamic — `ui::viewport::set_live_height` rebuilds the `Terminal` to grow/shrink it around a permission card or streaming markdown tail (ratatui fixes inline height at creation; rebuild failures degrade permanently to the fixed base height). The caret is real (`frame.set_cursor_position`, CJK-correct via `unicode-width`). Rendering/input live in `crates/holmes-cli/src/ui/`: `theme` (semantic colors + glyphs, quantized once at `init_theme` to the terminal's color level), `wrap` (word-aware style-preserving wrapping — scrollback needs exact row counts before `insert_before`), `input` (the ONE stdin reader thread both loops drain, + resize debounce), `keys` (`KeyOwner`/`EscStep`: which surface owns the keyboard and what Esc peels off one level at a time — the single source of truth for both dispatch and hint text), `viewport` (dynamic live-region height), `permission` (Ask-mode approval card + `InlineApprover` bridge), `blocks` (structured tool blocks), `diff` + `highlight` (syntect), `markdown` (streaming markdown), `buffer` (segment input buffer with atomic paste chips), `completion` (`@path` fuzzy file completion). Slash commands get a `⌘` autocomplete row while the input starts with `/`; all slash commands are handled by delegating to the shared `chat.rs::handle_slash_command` (the viewport is suspended so its `println!` becomes clean scrollback, then `SlashResult` is applied). A `TerminalGuard` (RAII) + panic hook **always** restore the terminal (no raw-mode leak on error/panic). If the terminal can't host an inline viewport (cursor-position query fails, e.g. some tmux/SSH), it **auto-falls-back** to the classic UI via `tui::run_tui_with_context`.

**Ask-mode permission card.** With permission mode `ask`, the runtime's `ApprovalHandler` is `ui::permission::InlineApprover`: it bridges the blocked tool call to the UI over a channel, and the busy turn loop opens a `PermissionCard` in the live region (above the input box; a compact one-liner when the viewport can't resize). The card owns every key until resolved; "always allow" answers are cached **for the session** by tool name (and by command prefix for `execute_command`), so repeat calls auto-approve without a card. For `execute_command` the cache matches per command **segment**: compound commands (`ls && rm -rf x`) are split with tree-sitter (`ui/cmdsplit.rs` — top-level commands joined by `&&`/`||`/`;`/`|`, pipes included; command substitutions stay opaque, unparseable input degrades to a single whole-line segment), and the call skips the prompt only when EVERY segment is covered by a cached prefix — a dangerous tail can never hide behind an approved head. The card lists the segments, authorized ones muted with `✓`, pending ones with `●`, and the Always option (with its ←/→ word granularity) applies to the **first unauthorized segment** only, so approval converges segment-by-segment instead of a wholesale grant. A rejection's operator feedback is pushed into the shared steering queue so the agent sees *why* the call was denied at the next iteration boundary, and the verdict line is committed to scrollback. `AgentRuntime::set_approver` installs it per turn.

**Tool blocks & diffs.** Tool calls render as structured `ui::blocks::ToolBlock`s paired by `call_id` across `ToolStarted`/`ToolFinished`: running blocks show a status line with a wave animation in the live region; finished blocks commit to scrollback with a three-state fold (collapsed one-liner / expanded output / full), and consecutive finished read-only blocks aggregate into one verb-summary line (`Read 3 files · Searched 1 pattern`) to keep recon quiet. `edit_file`/`write_file` blocks rebuild a unified diff from the tool arguments (`ui::diff`, no `+`/`-` prefixes — insert/delete rows carry a theme background band with a line-number gutter), syntax-highlighted per fragment via syntect (`ui::highlight`; flat red/green fallback on 16-color terminals or unknown extensions).

The **legacy full-screen TUI** (`tui.rs`, alternate screen) is retained as the fallback and reachable via `HOLMES_CLASSIC_TUI=1`. The legacy Reedline REPL (`chat.rs`) is reached via `holmes repl`, `--repl`, or `-q`. All surfaces consume the same `ChatContext` / `run_runtime_input_with_sink` from `chat.rs` — the shared "session + runtime plumbing" library (its `approver` parameter is where the inline UI's `InlineApprover` plugs in). When changing the agent loop or runtime wiring, expect all surfaces to be affected. (ratatui 0.30's `ratatui::crossterm` is 0.29, now unified with reedline and `tui.rs` — the old two-crossterm-version split is gone.)

35 slash commands are registered in `commands.rs::CommandRegistry` across eight categories (`Goal / 工具 / 工作流 / 会话管理 / 交互控制 / 配置 / 退出 / 信息`); `all_command_hints` powers tab-completion in Reedline and the `Ctrl+L` command palette in the TUI.

**Inline-UI input conveniences (`inline_ui.rs`, not registry commands).** `@path` in a message inlines that file's contents into the prompt sent to the agent (`expand_file_mentions`, 64 KB cap, unresolved `@tokens` left literal) while the transcript shows the original; typing `@` also opens a fuzzy path-completion list above the input box (`ui::completion`, nucleo matcher on a background worker with a generation fence against stale responses, ghost-text suffix for the top candidate, Tab/↑↓/Esc handled via `KeyOwner::FileCompletion`). Large pastes collapse into an atomic `[Pasted: N lines]` chip (`ui::buffer`) — the caret skips over it, Backspace deletes it whole, and the real content is only expanded on submit (bracketed paste is what lets the input thread see a multi-line paste as one event). `!cmd` runs a shell command locally (`run_shell`, `$SHELL -c`) and commits its output to scrollback — operator convenience, not routed through the agent or egress guards. **Plan-mode approval loop:** `/plan [objective]` saves the current permission mode and switches to `ReadOnly` (recon/read allowed, mutation/exploit blocked) so the agent investigates and proposes a plan via `write_todos`; `/approve` (alias `/go`) restores the saved mode and tells the agent to execute; `/reject [note]` (alias `/revise`) stays read-only and asks for a revised plan. State lives on `App.plan_prev_mode`; the status row shows a `◇ PLAN` indicator while awaiting approval. `run_turn_labeled` lets these show a concise label while sending a longer framing prompt. During a turn the runtime future is driven through a `tokio::select!` loop against the channel-backed `ChannelSink`, the approval-request channel, and the input thread, paced by `tick_demand` (fast 120ms tier while the spinner/wave animates, slow 500ms tier while an approval card parks them; idle is fully event-driven — zero ticks). Key bursts are drained and rendered once per batch (`drain_pending`), frames are wrapped in DEC-2026 synchronized updates, and Esc/Ctrl+C semantics come from `EscStep` (interrupt turn → clear input one level at a time). In-progress type-ahead is echoed in the input box; completed lines are pushed into the shared steering queue DURING the turn (`dispatch_busy_key`), so the runtime injects them at the next iteration boundary (see "Steering & background-task safety point"), and whatever the turn never drained transfers into `queued_turns` as follow-up turns.

### LLM client

`holmes-llm::LlmClient` is multi-provider over a single wire format (Anthropic Messages). `FailoverChain` tracks per-endpoint health (`consecutive_failures`, `last_failure`); `RateLimiter` enforces per-provider RPM; `RoleAssignment` routes calls by role (`attack_agent / supervisor / compressor / skill_evolver / goal_evaluator`) to a chosen provider. Errors are classified as retryable/rate-limit/permanent in `error_classifier.rs`; retries use exponential backoff. To add a different vendor, implement an adapter that translates to/from `AnthropicRequest`/`AnthropicResponse` (see `anthropic.rs`) — do not introduce a new wire format alongside.

**Prompt caching.** `AnthropicRequest::from_messages` (`anthropic.rs`) puts ephemeral `cache_control` breakpoints on the **last tool** (caches the whole stable tool array), the **system prompt** (`SystemBlock`), and — rolling — the **last content block of the second-to-last message** (`set_last_block_cache_control`), so the *growing conversation history* is cached across turns instead of reprocessed at full price every turn. The final message carries the volatile per-turn transient situation frame and is deliberately left after that breakpoint (uncached). (Before the rolling breakpoint, only system+tools were cached and long sessions re-billed the entire message history every turn.)

**Streaming.** `llm.stream: true` (now the default) makes `call_provider` read the SSE body **incrementally** via `resp.bytes_stream()`: each complete `data:` line is passed to `anthropic.rs::sse_line_text_delta` and assistant text deltas are accumulated into a **per-attempt buffer**, committed to the `on_text` callback only once that attempt fully succeeds (stop reason present, no terminal error frame) — a failed attempt that triggers failover never leaks its partial output to the UI, so displayed text always matches the authoritative response. The full body is still accumulated and handed to `parse_sse_response` to build the authoritative `LlmResponse` (tool calls, stop reason, usage). The callback is threaded through the stack: `LlmClient::chat_completion_streaming` → `LlmBackend::chat_completion_streaming` (async_trait; default delegates to non-streaming, so scripted/static test doubles need no changes) → `DeliberationEngine::decide_streaming` → `runtime.rs::decide_with_overflow_retry` builds a closure that emits `RuntimeYield::TextDelta` to the sink (only the first, non-overflow decide streams). The inline UI accumulates deltas into `ui::markdown::MarkdownStream` and renders them as **markdown with checkpoint freezing**: each throttled refresh pass (≥120ms, only on newline boundaries, via `refresh_markdown`) re-renders the accumulated source, commits newly *closed* blocks to scrollback (immutable once `insert_before`d), and shows the still-open tail in the live region (capped at `min(MAX_TAIL_ROWS=20, screen_height/2)`). Any non-delta yield finalizes the stream (`finalize_stream` commits the rest), and a trailing full-text `MessageToUser`/`FinalAnswer` that only repeats the streamed text is **suppressed**. The line-REPL/one-shot (`CliRuntimeSink`) and classic TUI ignore `TextDelta` and print whole blocks. Requires reqwest's `stream` feature + `futures`.

**Extended thinking.** `llm.thinking_budget > 0` makes `call_provider` add `thinking: {type: enabled, budget_tokens}` (and bump `max_tokens`, drop `temperature`). Signed thinking blocks in the response are captured into `LlmResponse.thinking_blocks` (not flattened to text), carried onto the recorded assistant `Message.thinking_blocks`, and re-emitted **first** (with signature) in that turn's assistant content by `from_messages` — required by the API when a thinking block precedes a `tool_use`. Off by default. (Verified live end-to-end against DeepSeek's Anthropic endpoint with `deepseek-reasoner`.)

### Harness

Add a scenario YAML to `scenarios/`, point it at scripted LLM responses and mocked tools, declare expectations, and `cargo test -p holmes-harness` exercises it through a real `AgentRuntime` with an in-memory `SessionDB` and `ScriptedLlmBackend`. Transcripts are written to `crates/holmes-harness/sessions/<uuid>/transcript.jsonl` (gitignored as artifacts). Use this in preference to mocking the runtime when adding deterministic regression tests for agent behavior.

### Bundled Pentest methodology (Pentest mode default)

`skills/pentest-lyan/` ships with Holmes as a bundled skill (Pentest-Lyan v2.3, MIT, from `HeaSec/Pentest-Lyan`). It is wired into the default session in two layers:

1. **Hardcoded methodology** — `project_knowledge.rs::PENTEST_METHODOLOGY` (the精炼 essence: three phases, 12-dimension threat model, 9 Banned Patterns, `coverage_note` 三问) is injected into the system prompt by `build_system_prompt(..., mode)` **only when `mode == SessionMode::Pentest`** (the default mode). Other modes are not polluted.
2. **On-demand details** — The full `SKILL.md`, `gates.md`, `references/*.md`, `schema/*.json` stay on disk; the existing skill auto-discovery (`skills.dir = "skills"`) indexes them, and the prompt points the model to `Read` specific references when it needs depth.

When changing `SYSTEM_PROMPT` or `PENTEST_METHODOLOGY` in `chat.rs`/`project_knowledge.rs`, remember the methodology is a **default operating standard, not a slash command** — the model is expected to apply Banned Patterns (e.g. "200 ≠ vulnerability", no hardcoded victim IDs in cross-role tests, `not_vulnerable` must list `unruled_out`) without being asked. Tests `pentest_mode_injects_pentest_methodology` and `non_pentest_mode_skips_pentest_methodology` lock in the per-mode behavior.
